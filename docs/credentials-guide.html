01

Meta Marketing API

Not set up

You need a Business Manager system user token — not a personal one. Personal tokens are tied to a human account and die when that person leaves, changes their password, or their session expires. This report runs unattended every Monday, so it needs a token that outlives all of that.

Whoever does this needs admin rights on the Business Manager that owns the ad accounts. Budget about 30 minutes.

META_ACCESS_TOKEN
Long-lived system user token with ads_read
META_PURCHASE_ACTION_TYPE
Which action type carries purchase value — confirm against real data
How to get the token

Create or identify a Meta app

Go to developers.facebook.com/apps. Either reuse an existing business app or create a new one — choose the Business app type, since that is what can hold Marketing API permissions.

Note the App ID. You need it when generating the token, and the app must belong to the same Business Manager as the system user.

Add the Marketing API product

In the app dashboard, find Marketing API in the product list and add it. Without this, the ads_read scope is not offered when you generate the token.

Terminology changed in May 2026. What used to be called "Standard" and "Advanced" access is now the Marketing API Access Tier, with Limited Access and Full Access levels. Limited Access is enough to start — this report makes roughly a dozen calls a day, far inside any rate limit. Do not get stuck hunting for the old menu names.

Create the system user

Open Business Settings and navigate to:

Business Settings › Users › System users › Add

Give it a name that says what it is for — "Editor Performance Report" — so nobody revokes it in a year wondering what it was. Assign the Admin role.

Assign all 11 ad accounts to it

With the system user selected, click Add Assets, choose Ad Accounts, and tick every one of the 11 IDs in the table below. For each, enable at minimum View Performance.

This is the step people miss. Creating the system user does not give it access to anything. A token generated without assigned assets authenticates fine and then returns empty or permission-denied for every account — which looks like a code bug rather than a setup gap.

Generate the token

On the system user, click Generate New Token. Select the app from step 1, then tick ads_read. That is the only scope this report needs — it never writes to your ad accounts.

Tokens default to expiring in 60 days. Look for the expiry option and choose the non-expiring setting, or the Monday report silently stops working two months from now. If your policy requires expiring tokens that is fine, but set a calendar reminder to rotate it — and expect the dashboard to show failed accounts when it lapses.

Copy the token immediately. Meta shows it exactly once. If you lose it you generate a new one; there is no way to read it back.

Hand it over securely

Send it through a password manager or secrets vault, not email or Slack. It grants read access to every ad account you just assigned. It goes into META_ACCESS_TOKEN.

Then confirm it works
npm run preflight:meta  # must print 11 green rows npm run preflight:meta -- --save # also saves each account's timezone

This checks every account individually and reports exactly which ones fail, so a missed asset assignment shows up immediately rather than as a mysterious gap in the report. The --save run also stores each account's reporting timezone, which the week and 30-day boundaries depend on.

The second variable: which purchase action
Decide this against real data Purchase value comes out of Meta's action_values array, and omni_purchase and offsite_conversion.fb_pixel_purchase can differ materially — the first includes app and in-store conversions, the second is pixel-only.

Pull one account both ways and compare against what Ads Manager shows for the same date range, then set whichever matches. Getting this wrong mis-states Meta ROAS with no visible symptom: the page looks completely normal.

02

Pipes API

Unconfirmed

This one is not just a credential. It is an open question about whether the report can work at all, and the spec says to settle it before scoping anything else. Nobody has confirmed yet that Pipes can attribute revenue to an individual Meta ad.

PIPES_API_BASE
Endpoint at admin.fourammedia.com/platforms
PIPES_API_KEY
Auth credential — method still unknown
PIPES_ALLOW_UTM_FALLBACK
Leave false unless question 3 is answered yes
How to get it

There is no self-service portal here — this comes down to finding the right person.

Find who owns Pipes at Four AM Media

Whoever administers admin.fourammedia.com — likely whoever set up the tracking originally. Ask them directly whether the platform exposes an API, and if so, for documentation and a key.

If there is no documentation, log in and look

Check for a Settings, Integrations, or Developer area — that is where an API key usually lives. Failing that, open the browser network tab while loading a revenue report and look at what the dashboard itself calls. Those are the same endpoints an integration would use.

Export one report and inspect the columns

Even before an API exists, a CSV export answers the most important question: is there an ad-level identifier in the data at all? Look for a column holding a Meta ad ID, or a UTM content value carrying the ad name. If neither is there, the API will not have it either.

Send back the five answers below

Those determine whether we wire it up, and how. Write them into docs/pipes-findings.md along with a sample response.

The five questions the spike must answer
  • What is the auth method, and what shape are the requests and responses?
  • Can a revenue row be tied to one Meta ad ID? A direct field, or only a UTM content value?
  • If UTM content — does it carry the ad name consistently across all ten accounts? A convention that holds for eight and not two produces a report that is quietly wrong for those two.
  • What share of Pipes revenue fails to join? It has to be near zero. The dashboard already computes and displays this, and warns above 2%.
  • What timezone are the timestamps? If UTC, they need converting to account-local before bucketing, or revenue lands on the wrong day and leaks across the week boundary.

If it cannot attribute to an ad, we stop

Every figure in this report is a sum over individual ads, because editors are identified by a token in the ad name. Revenue that cannot be tied to an ad cannot be tied to an editor.

If questions 2 and 3 both come back no, the agreed call is to stop and escalate: no Pipes ROAS, no verdicts, an explicit blocked state on the dashboard. Specifically not substituting Meta ROAS — the targets are Pipes-based, so that would put green checks against a number nobody agreed to.

03

Ads Manager URLs

Awaiting capture

Not a credential — two URLs somebody copies out of Ads Manager by hand. Anyone with access to one ad account can do this in about ten minutes.

ADS_MANAGER_ACCOUNT_URL_TEMPLATE
Account view — needs {ACCOUNT_ID} {START} {END}
ADS_MANAGER_EDITOR_URL_TEMPLATE
Same plus {TOKEN}, with the ad-name filter applied
How to capture them

Open any one of the ad accounts

Go to Ads Manager and switch to the Ads tab — ad level specifically, not campaigns or ad sets. The report links to creative detail, so the breakdown has to be by ad.

Set a custom date range, then copy the URL

Any range will do; you are capturing the shape, not the dates. Copy the whole URL from the address bar — that is your account template.

Now add the ad-name filter

Filters › Ad Name › contains › Santiago

Use any real editor token. Then — this is the part that matters — confirm the table actually narrows to that editor's ads before you copy anything.

Copy that URL too

That is your editor template. It will contain a filter_set parameter that the first one does not.

Swap in the placeholders

In both URLs, replace the parts that vary:

act=… → {ACCOUNT_ID}
start date → {START}    end date → {END}
the editor name → {TOKEN}

Dates are substituted as YYYY-MM-DD. If Ads Manager uses a different format in the URL, send both URLs as-is and we will adjust the substitution.

Why by hand and not in code Meta's filter encoding is undocumented and changes between versions. A URL that silently drops its filter looks identical until you click it — you would get a full unfiltered account view while believing you were looking at one editor's ads, and the numbers would look plausible. Capturing from a view you have confirmed works is the only reliable way.

Until these are set, the dashboard shows an amber "links unverified" banner. The same walkthrough, plus a click-through checklist for launch, is in docs/ads-manager-urls.md.

04

Hosting and app secrets

Working locally

All four already work on the development machine. Production needs a hosted database and freshly generated secrets — the local ones live in a gitignored file and should never travel to a deployed environment.

DATABASE_URL
Local Docker Postgres today; needs hosted Supabase or Neon for production
APP_PASSWORD
The shared password for the login gate — change it for production
SESSION_SECRET
Signs the session cookie — 32 characters or more
CRON_SECRET
16+ chars; Vercel Cron sends it as a Bearer token
Getting a production database

Create a project on Neon or Supabase

Either works — both have free tiers that comfortably fit this workload, which is one small write per day and a handful of reads per page view. Neon is the slightly simpler option if you only want Postgres and no other services.

Copy the connection string

Both providers show it as a postgres:// URL in the project dashboard. Make sure you take the pooled connection string if offered one — serverless functions open and close connections constantly. It goes into DATABASE_URL.

Run the migrations against it

npm run db:migrate  # create the tables npm run db:seed     # 10 accounts, 5 editor tokens

The seed is safe to re-run: it updates names and account mappings but never overwrites a target you have since confirmed in the database.

Generating the three secrets

Run this three times, or twice plus a password of your choosing:

node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

SESSION_SECRET must be at least 32 characters and CRON_SECRET at least 16 — the app refuses to start otherwise, rather than running with weak signing keys. APP_PASSWORD is the one humans type, so make it something shareable but not guessable.

Set all of these in your host's environment variables, not in a file in the repository. On Vercel that is Project Settings › Environment Variables. The local .env.local is gitignored and stays on the dev machine.
05

Once the keys land

Ready to switch

The live clients slot in behind interfaces the pipeline already uses, so nothing in the computation or the UI changes.

  1. Implement the live Meta and Pipes clients against the existing interfaces.
  2. Set USE_FIXTURES=false.
  3. Run the 13-month backfill — first-delivery dates come from real delivery history, and until it runs an ad from March looks brand new, so the new-vs-holdover split is wrong.
  4. Click through the generated Ads Manager links and confirm the filter is actually applied.
